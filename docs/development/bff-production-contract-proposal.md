## D01 — Minimal versioned authentication transport

| Operation | Proposed exact behavior |
|---|---|
| `GET /bff/v1/session` | JSON `{schemaVersion:"bff-session-v1",authenticated:boolean,csrfToken:string}`; no identity claims, customer assignments, tokens, session reference or grant list. The opaque synchronizer token binds to the current anonymous/authenticated context. Only transport CSRF cookie issuance occurs; no product/authority mutation or store ticket creation/revocation. Ordinary existing authenticated-request idle bookkeeping remains governed by the approved shared-store policy. Response always no-store. |
| `POST /bff/v1/sign-in` | Accept only a top-level form POST with `application/x-www-form-urlencoded` interpreted as UTF-8 when charset is absent; explicit non-UTF-8 charset rejects. Accept exactly one `__RequestVerificationToken` field (nonempty, maximum 4096 characters), body maximum 8192 bytes. Require the fixed configured same origin and valid synchronizer token. No caller return URL or scope. An already authenticated request is denied with 409; it cannot create an additional ticket or silently replace its existing session. When configured activation is disabled, 403 and no provider activity. Otherwise supported single-tenant code+PKCE challenge; request fresh authentication with `max_age=0`; the browser follows the supported challenge redirect; completion returns only to fixed `/bff/v1/session`. The UI obtains the synchronizer token from the session operation and submits a hidden form through normal browser navigation; it does not follow the provider redirect through fetch. No scope/admission inferred from claims. |
| `POST /bff/v1/sign-out` | Require authenticated session, fixed configured same origin and synchronizer token in `X-CSRF-Token`; `application/json` UTF-8 containing exactly an empty object, maximum 8192 bytes. Revoke this store session before clearing cookies; return 204. This ends the local product session; it makes no global/provider logout claim. Store/authority failure denies without reporting successful revocation. |
| Existing `/bff/signin-oidc`, `/bff/signout-callback-oidc`, `/bff/signout-oidc` | Framework-owned protocol callbacks only; retain supported state/nonce/PKCE/correlation guards, exact tenant/client validation and narrow cookie path. The OIDC `form_post` callback is handled by the supported handler rather than the application form/JSON/Origin/CSRF guards; nonce, state and correlation validation are mandatory. This is no general callback or cross-origin exemption. No generic callback forwarding. Remote sign-out never supplies product customer authority. |

Application precedence: unknown path 404; unsupported method 405; disabled sign-in 403 before parsing or provider activity; sign-out missing authentication 401; authenticated sign-in 409; origin denial 403; bounded content/schema parsing rejects invalid content type, fields, token length or body with 400; only then synchronizer validation/current-authority denial 403. Parsing never echoes the body. Anonymous session/sign-in do not require an existing login. Callback paths use their supported protocol handler and fail closed when activation is disabled. Successful session JSON is 200; successful sign-in is the supported provider redirect; sign-out is local 204. No body content is echoed in errors. Errors carry no provider/identity detail. No CORS credentials, browser bearer scope, session-list/revoke-other/reauthentication/customer-data operation, UI adoption of the local-demo contract or public admin route is introduced. Health endpoints keep the already approved diagnostic contract. Login/session endpoints are absent from the independent disabled host until D01 is accepted.

## D02 — Authentication/session-bound authority

Split current subject-only admission into (a) current provider/product subject eligibility and (b) authentication evidence bound to the particular protocol completion or opaque store session. The initial timestamp comes from the signature/issuer/audience/state-validated OIDC `auth_time` response to the fresh-authentication request; missing, future, malformed or stale time denies. Preserve the issuance timestamp in a protected, nonce/correlation-bound pending challenge transaction with a maximum 15-minute lifetime and single successful consumption. Require integer UTC `auth_time` >= challenge issuance rounded down to integer UTC seconds, <= validation time, and authentication age strictly less than 15 minutes. The callback first passes all supported token/protocol validation; only then can this transaction complete. Replay, expired or missing transaction denies. Configure the required optional claim in Entra only after separate environment review and verify actual signed-token emission; never assume the claim is present or silently alter handler expiry defaults. Never substitute current server time or the newest authentication of another session.

Session checks bind immutable tenant/object identity, exact session reference, original authentication, provider-status cutoff and monotonic security version. Security version/assignment revocation applies on the next request. Role changes revoke old sessions; no subject-wide MFA boolean or timestamp can admit another session. Existing idle30min/absolute8h/provider<15min limits and per-request product-state lookup remain unchanged. Every missing binding/evidence source denies. Preserve the approved organizational-only identity rule: resource-tenant `tid` alone cannot admit a Microsoft-account-backed guest. Reject the documented personal-account identity-provider forms, and require reviewed organizational origin evidence for B2B guests; unknown origin denies. Actual provider claim semantics require negative provider tests before activation.

For the first integration, privileged authentication verifier remains deny-by-default unless the separately reviewed Entra authentication-context and phishing-resistant strength evidence is bound to the exact subject/session/security version/action. Do not treat `amr`, a coarse app role, a local flag, email or a different session as sufficient. No privileged operation is enabled by accepting D01/D02.

## D03 — Product-side enrollment and provider retrieval boundary (deferred decision)

This section is not ready for production-adapter approval. Exact versioned enrollment/assignment/guest records, protected administration source, migration and reader/admin identities require a separate concrete decision. Until then only internal contracts with default-denying implementations may be prepared.

Persist explicit product enrollment/assignment/guest lifecycle only in module-owned control-plane tables, via a controlled migration and trusted administration path. No automatic enrollment at sign-in and no public administration operation. Read adapters enforce current active assignment, scope, guest sponsor/expiry/review, customer policy and resource state before any customer-store lookup. Missing or contradictory state denies. Existing product role/action/evidence rules remain authoritative; test fixtures cannot become runtime assignments.

Proposed provider reader: a distinct managed-identity application-only Microsoft Graph read adapter for **only already enrolled tenant/object IDs**, using `GET /v1.0/users/{objectId}?$select=id,accountEnabled,userType,externalUserState,signInSessionsValidFromDateTime`. No user listing, profile/default fields, group/member graph, sign-in log ingestion or Graph write method. The proposed consent is `User.Read.All` only, which nevertheless permits tenant-wide profile reads and requires separate exact access approval before provisioning. Do not request Directory.Read.All, User.ReadWrite.All or User.EnableDisableAccount.All. If the approved read permission cannot supply required properties, fail closed and return to security review; never expand permission automatically.

Microsoft describes `User.Read.All` as the least application permission for Get user, and separately identifies a read/write combination for accountEnabled. That is not proof that the selected restricted runtime query succeeds. Actual least-permission property access, cutoff semantics and unavailable/ambiguous responses require provider-spike evidence before activation. Provider account state alone does not verify CA or all grant changes. Product-role updates remain attributable, security-versioned authority changes; current provider-app-role revalidation needs its own accepted source/contract before live use. Its absence denies; local product roles cannot substitute for current provider app-role evidence.

References: [Get user permissions](https://learn.microsoft.com/en-us/graph/api/user-get?view=graph-rest-1.0), [user cutoff property](https://learn.microsoft.com/en-us/graph/api/resources/user?view=graph-rest-1.0), [signed identity claims and personal-account guest origin](https://learn.microsoft.com/en-us/entra/identity-platform/id-token-claims-reference). This is an implementation proposal, not live Graph consent.

## D04 — Proxy, keys and audit integration (deferred decision)

This section is not approval of a production composition. Exact proxy networks, Data Protection application discriminator, versioned/versionless Key Vault URI behavior, key recovery, narrow grants, and a versioned audit event/store contract are unresolved deployment decisions. Blob key persistence is proposed, not an already accepted implementation detail.

Development tests use direct real HTTPS. Production uses an explicitly configured trusted proxy network/addresses and fixed allowed host/origin, never blanket forwarded-header trust. Only the reviewed Container Apps ingress path may supply original HTTPS/host data. The actual trust configuration is a deployment input requiring negative spoofing and deployed-network proof.

The shared replica Data Protection ring is persisted in a dedicated private control-plane Blob object and protected using the approved Key Vault managed-identity pattern. Narrow key/blob grants, key version/rotation/recovery and database roles remain separately reviewed deployment inputs; no storage or key grant is made by local implementation. No startup migration or fallback plaintext/ephemeral production key ring.

Write payload-free append-only product security audit under the [approved audit policy](../security/health-assessment-audit-policy.md). That policy is not a concrete event schema. The proposed session/audit design must commit issuance plus its event atomically, or supply a reviewed fail-closed compensation path that leaves no admitted session after audit failure. Revocation plus its event needs an atomic transaction or explicitly reviewed durable failure semantics; never claim an already committed revoke was rolled back or report success before its required event is durable. Failure cannot return successful sign-in/session revocation or a privileged action. Concrete writer/store identity and cleanup/12-month preservation follow the existing audit policy; no new retention default is selected. Operator, migration, ordinary ticket and customer roles stay distinct.
