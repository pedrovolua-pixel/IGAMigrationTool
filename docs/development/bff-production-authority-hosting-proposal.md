## P01 — Exact internal authority records

All records have a fixed schema version, closed fields and types. Unknown enum/version/extra field, empty identifiers, duplicate keys, invalid UTC times, malformed digest or conflicting authority denies. GUIDs are immutable nonempty canonical IDs, revisions/security versions positive signed64-bit integers. Times are UTC instants; no caller can manufacture a trusted observation or actor. Types reuse existing `IdentityPolicy` roles, grant conditions, scope and evidence keys; no new role permission is inferred.

| Candidate v1 record | Exact fields and constraints |
|---|---|
| `SubjectEnrollmentV1` | Key `(tenantId,objectId)`; `revision`; lifecycle `Pending/Active/Suspended/Revoked`; explicit origin `InternalOrganizational/ExternalOrganizational`; `homeTenantId`; `enrolledAtUtc`; `approvedDecisionId`, immutable `approvedBySubject`, `approvedAtUtc`. Internal home tenant equals reviewed resource tenant; external home must match reviewed nonconsumer organizational evidence. No email/UPN/display-name keys. Sign-in cannot enroll, reactivate or change origin. |
| `HumanAssignmentV1` | `assignmentId`, exact subject FK, `customerId/projectId/environmentId/assessmentId`, existing `HumanRole`, `active`, `startsAtUtc/expiresAtUtc`, distinct evidence-category keys and existing grant-condition values, `revision` and the same decision attribution. Composite ownership constraints bind scope. No wildcard or descendant inference. Duplicate `(subject,role,scope)` denies rather than merging permissions. |
| `GuestLifecycleV1` | Enrollment FK, sponsor subject, `assignedAtUtc/expiresAtUtc/lastReviewedAtUtc`, opaque engagement reference/revision, `sponsorOrEngagementChanged`, decision attribution. Active sponsor; expires after assignment and at most90days later; review no later than30days; future review denies. Sponsor/engagement change requires renewed reviewed authority. Applies to external origin independently of Graph `userType`. |
| `ProviderRoleBindingV1` | Reviewed resource tenant, BFF client and resource service-principal object IDs; exact four nonzero app-role GUIDs mapped bijectively to the four approved BFF roles; manifest revision/SHA256 and decision reference. | `ProviderObservationV1` | Exact subject and tenant/client/resource binding; sequence; `startedAtUtc/completedAtUtc`; captured enrollment revision and subject security version; returned subject ID; strict boolean `accountEnabled`; known `userType`; invitation state; non-null UTC resource cutoff; sorted distinct exact bound role IDs; explicit completeness; safe correlation. Cannot enroll, grant detailed roles, clear suspension/revocation or supply original authentication/MFA. |
| `OperationReceiptV1` | Globally unique server-generated `operationId` (the authority `commandId` for those commands); trusted issuer/writer and actor binding; allowlisted operation kind; exact target subject/scope and opaque old/new session references where applicable; canonical command digest; committed outcome/time; resulting authority revision/security version; distinct linked event IDs. Use `identity_sessions.subjects.security_version` as the one revocation authority; do not create independently incremented product/session counters. `IdentityPolicy` owns enrollment/assignments; `IdentitySessions` owns challenge/ticket rows. Production projections must reconcile them in one trusted snapshot and validate the exact resource revision before lookup/serialization.

Allowed proposed administration commands: enroll-as-Pending, approve/activate explicit enrollment, suspend/revoke subject, set/revoke exact assignment, approve/renew external lifecycle, record sponsor/engagement change, and revoke exact/all subject sessions. Activation from Suspended requires a new attributable decision; Revoked is terminal for that enrollment record. Any later re-enrollment needs a separately approved process, not a provider refresh. No arbitrary patch or public administration operation. Synthetic commands use explicitly fictional trusted actors; they cannot seed real runtime assignments. Actual named-operator transport and privileged exact-session MFA/CA remain separately reviewed inputs.

### Transaction and provider publication

1. Trusted administration supplies actor, decision and exact command/digest; lock subject first, then owned target/tickets. Resolve any existing operation receipt after the subject lock and before expected-revision validation. Exact issuer/actor/operation/target/digest match returns its recorded outcome without mutating; mismatch denies. Only a new command checks expected revision and scope/ownership invariants. Read fresh trusted time after waits. New enrollment has no existing subject row: create the Pending subject/enrollment/version and receipt/event atomically with unique immutable subject keys; concurrent insert conflicts roll back and resolve the existing receipt or deny, never overwrite an enrollment.
2. Change authority; increment subject security version once and revoke affected subject sessions; append attributable event/receipt in the same transaction. Commit before reporting success. No direct caller table writes.
3. Same commandId/same target and digest resolves prior outcome without another version/event. Same ID/different command denies. Revision conflict requires reread and a new reviewed decision.
4. Read provider outside database locks only for already enrolled exact IDs. Publish under subject lock only if captured product revision/security version still match, sequence/time/cutoff are monotonic, result is complete and no newer observation won. A future or regressing cutoff denies. Sample trusted `startedAtUtc` before the first provider await. Require `startedAtUtc <= completedAtUtc <= publicationNow`; bind `provider_checked_at` to that conservative start, never completion/publication-now. Recheck `publicationNow - startedAtUtc < 15 minutes` after network/lock waits and immediately before commit; expired result denies without advancing freshness. Requests recheck the same conservative timestamp against fresh trusted time. Slow reads cannot manufacture a new 15-minute window.
5. Authoritative account or role eligibility change clears effective validity, advances security version and revokes old sessions atomically. Missing, ambiguous or failed response never refreshes `provider_checked_at`; current attempted authorization denies. An observation cannot reactivate suspended/revoked authority. Lost refreshes cannot overwrite a newer revoke.
6. Every request checks product authority, exact session version/roles and scope. Provider evidence remains strictly younger than15minutes; no authorization cache exceeds the already approved limit. Refresh is not a guaranteed instantly current Entra view. Known compromise/removal triggers product denial first, with separately authorized provider administration later.

Mutable operational authority and revoked enrollment/command receipts/challenge/ticket cleanup do not acquire a retention duration from this proposal. Those lifecycles need a concrete data/operations decision before live use; revocation tombstones cannot be removed in a way that resurrects access.

## P02 — Provider queries, roles and external users

Proposed user query, restricted to the enrolled immutable object:

`GET /v1.0/users/{objectId}?$select=id,accountEnabled,userType,externalUserState,signInSessionsValidFromDateTime`

Microsoft documents application `User.Read.All` for Get user and identifies an additional read/write permission combination for `accountEnabled`. This is a property-access proof gate; no write permission is recommended or provisioned. If the exact read cannot return a trustworthy required property under the approved permission, deny and return for review. [Get user](https://learn.microsoft.com/en-us/graph/api/user-get?view=graph-rest-1.0).

Proposed initial direct-user role query:

`GET /v1.0/servicePrincipals/{reviewedResourceSpId}/appRoleAssignedTo?$filter=principalId eq {enrolledObjectId}&$select=id,appRoleId,principalId,principalType,resourceId`

Require exact resource/subject, `principalType=User` and bound approved role IDs. Prove filtering/property/pagination behavior live. Follow only validated HTTPS Graph continuation URLs for the same configured API/resource/query; hostile/missing/incomplete pages deny. No user enumeration, group/member traversal, sign-in logs, Graph writes or browser delegated scope is added.

Application `Application.Read.All` is documented for the resource endpoint. It remains tenant-wide application/service-principal read permission; fixed application queries are not provider-scoped consent. Microsoft warns grants/removals can replicate late. [Resource role assignments](https://learn.microsoft.com/en-us/graph/api/serviceprincipal-list-approleassignedto?view=graph-rest-1.0), [permission scopes](https://learn.microsoft.com/en-us/graph/permissions-reference).

**Alternative requiring expanded review:** user `appRoleAssignments` includes direct group membership assignments but documents application `Directory.Read.All`; group licensing/effective membership/complete paging require proof. Nested groups are unsupported for enterprise assignment. No automatic permission escalation or implied group acceptance. Initial direct-only composition is a narrower proposed admission choice, not deletion of the approved future group option. [User role assignments](https://learn.microsoft.com/en-us/graph/api/user-list-approleassignments?view=graph-rest-1.0), [enterprise assignment](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/assign-user-or-group-access-portal).

External origin is independent of `userType`: an external user can be Member and converting Guest to Member does not change authentication source. Invitation Accepted is not organizational origin or product onboarding. An external Member must not bypass sponsor/home-origin/lifecycle checks merely because the current D01 admission object names its flag `IsGuest`; production projection must conservatively apply the external lifecycle boundary. Unknown origin denies. [B2B properties](https://learn.microsoft.com/en-us/entra/external-id/user-properties).

External admission requires explicit reviewed product onboarding, valid sponsor/assignment/review/expiry, exact reviewed nonconsumer home tenant, signed supported origin match, valid resource account/role/cutoff, and a reviewed source proving required home-account/session status. Token `idp` is not a home object identifier; no UPN/email heuristic or cross-tenant Graph consent is proposed. Resource revocation does not revoke external home-tenant sessions and may take minutes. Until the home-status trust contract and actual negative tests exist, external production admission remains denied. [Claims](https://learn.microsoft.com/en-us/entra/identity-platform/id-token-claims-reference), [cutoff property](https://learn.microsoft.com/en-us/graph/api/resources/user?view=graph-rest-1.0), [revocation limitations](https://learn.microsoft.com/en-us/graph/api/user-revokesigninsessions?view=graph-rest-1.0).

## P03 — Durable audit and uncertain outcomes

Proposed `security_audit.session_event_v1` is append-only with no arbitrary JSON/free text. Fields: fixed `schemaVersion`; unique `eventId`; server-owned `operationId`; trusted UTC `eventAtUtc`; verified actor kind `Human/Workload/Anonymous`; immutable tenant/object identity only when verified; writer workload/application/client binding; opaque correlation; typed action/outcome/reason enum; opaque session reference/security version when applicable; allowlisted authentication-evidence category. Authentication scope is Platform. Customer/project identifiers are nullable and may appear only after an independently authorized operation establishes scope. No fabricated customer association.

Initial typed actions: `SessionIssued`, `AuthenticationDenied`, `AuthenticationFailed`, `SessionRevoked`, `SessionRotated`, `SubjectRevoked`, `AuthorityChanged`. Outcomes `Succeeded/Denied/Failed`; bounded reasons `None/InvalidProtocol/AuthorityDenied/ProviderUnavailable/AuditUnavailable/Conflict`. Exact code-specific failure details remain private operational investigation, never free-form security events. Privileged reauthentication is represented only when its separately approved verifier exists; no synthetic boolean becomes production evidence.

Prohibited fields/values include tokens, cookies, lookup keys/hashes, protected ticket bytes, raw claims/provider errors, email/display names, customer evidence, prompts/responses, comments/reports, connection strings and credentials. Unknown property/action combination denies serialization. Audit is not an authority source.

| Mutation | Required transaction; success only after durable commit |
|---|---|
| Issue | Lock subject → validate current product/provider/session evidence → insert protected ticket and issuance event/receipt → commit → allow cookie. A burned challenge after later failure never admits a ticket. |
| Exact revoke | Lock subject then exact ticket → revoke → append event/receipt → commit → clear cookie/return204. Other sessions preserved. |
| Rotate | Lock subject then old ticket → revalidate → revoke old and insert new → append correlated event/receipt → commit → return replacement. Never silently replace expired authentication. |
| Subject/authority change | Lock subject/owned authority → update/increment version/revoke affected sessions → append attributable event/receipt → commit. |
| Ordinary idle touch | Existing bounded bookkeeping only; no invented audit event or policy change for each GET. |

After all subject/ticket/audit-stream lock waits and asynchronous work, recheck trusted time and every admission/authentication/provider deadline immediately before commit. Audit failure rolls back the mutation. Lost commit acknowledgment returns generic failure and does not claim rollback. Reconcile the durable operation receipt before any retry/success; do not replay a consumed OIDC transaction. A committed but unacknowledged issuance can leave an audited inaccessible ticket; no response may expose its protected bytes or replay the credential. A trusted internal revoke retry after a committed revoke resolves its receipt without a second event/version change. This is not a new browser operation: replaying a revoked cookie still gets the existing D01 unauthenticated denial, not receipt access. Operation/digest keys are internal and must not echo browser secrets.

Proposed audit ordering/integrity records are closed, not inferred from UUIDs:

- `AuditStreamV1`: exact approved environment stream ID, nonnegative 64-bit committed head sequence, head event SHA256, positive revision and approved writer-binding reference. One ordered authentication/authority stream per environment for this candidate; no attacker-created stream or customer stream inference.
- Every event also has `streamId`, positive 64-bit `sequence`, `previousEventSha256`, `eventSha256`. Enforce unique `(streamId,sequence)` and unique event ID. Under the same mutation transaction, lock the pre-provisioned stream head **after** subject/target locks, allocate head+1, append the event and update head atomically. First previous digest is64zero hex characters; empty stream has sequence0 and that digest. No sequence allocated outside the transaction. Overflow or absent stream denies.
- Hash SHA256 over UTF-8 RFC8785 canonical JSON of the closed event excluding `eventSha256`, including its previous digest. Canonical GUIDs/lowercase SHA256; fixed UTC `yyyy-MM-ddTHH:mm:ss.fffffffZ` representation;64-bit counters and security versions encode as canonical unsigned decimal strings to avoid JSON number rounding. Prohibit duplicate/unknown fields/nonfinite values. This is an internal integrity representation, not a new public contract. [RFC8785](https://www.rfc-editor.org/rfc/rfc8785).
- `AuditCheckpointV1`: fixed version, stream/environment/writer-binding reference, exact head sequence/digest, trusted captured UTC time and opaque witness/evidence reference. A separate approved reader/witness verifies the chain and reconciles event IDs against operation receipts. Deletion tombstones preserve the original sequence/digest and lifecycle authority so authorized purge is distinguishable from an unexplained gap. Restore verifies the witnessed head/tombstones and cannot reset the stream or authority versions.
- Local tests use explicit synthetic checkpoints. Real independently retained witness/signing trust, protected destination, checkpoint schedule and integrity-alert runbook remain live bindings; a database-local hash alone cannot prove integrity against a privileged operator. No new signer, permission or automatic retention schedule is selected.

Separate nonlogin function owner, migration executor, administration executor, observation publisher, ordinary ticket runtime, scoped audit reader and lifecycle operator. Functions have fixed schema-qualified objects/search path, no arbitrary SQL and no runtime direct update/delete on event or authority tables. Restrict PUBLIC execution. A runtime can request only its allowed exact-session transaction; administration and provider publication cannot be reached through browser input. Role and ownership choices must be verified with negative database tests before live grants. Nonlogin ownership and SECURITY DEFINER are not automatic proof of safe authority.

Approved audit lifecycle stays12months from event timestamp, then soft-delete filtered from ordinary reads; active purge within30additional days unless hold, max35-day rolling backups and restore tombstone replay. Separate lifecycle/tombstone metadata permits authorized lifecycle without ordinary event edits. Integrity checks must detect sequence gaps/unknown writers/time anomalies, and recovered authority may not regress or resurrect revoked sessions. No raw report/payload is stored.

**Unresolved production audit outage:** denying authentication while the audit store is unavailable does not itself preserve the required failure event. Neither stderr nor Application Insights is the audit record. Production activation needs an explicit reviewed durable fallback/reconciliation contract or a human-approved policy amendment for this precise outage; this proposal selects neither. Local failure tests prove denial/rollback, not complete production failure-event preservation. Do not expose the proposed production host until this dependency is resolved.

## P04 — Proxy and shared protection keys

Use the existing private Container Apps environment as the candidate boundary. The bootstrap's app `external:false` FQDN serves only that environment, unless an environment-level HTTP route explicitly exposes the app to other callers. It cannot be assumed to supply reviewed human BFF reachability. Inventory environment-level routes; absence or exact approved route targets are required deployment evidence. App `external:true` on a private environment may serve its internal load balancer to approved reachable networks without making the environment public. The named human browser path, DNS/certificate and reachability design still require explicit protected review; source-collector outbound HTTPS is not that design. No VPN/peering/gateway/public ingress is introduced. [Container Apps ingress](https://learn.microsoft.com/en-us/azure/container-apps/ingress-overview).

Proposed one-hop header contract: process only `X-Forwarded-Proto` and, if required, `X-Forwarded-For`; one rightmost trusted hop, actual immediate peer IP/CIDR proven by deployment. Never blanket trust VNet/proxy headers or clear trusted lists. Do not process forwarded Host/prefix initially. Require original Host exact canonical hostname and fixed D01 HTTPS Origin. Unsupported peer/chain/effective scheme/host denies authentication. Apply forwarded processing before HTTPS/authentication; use the API supported by pinned .NET 10.0.12. Health probes retain a separately bounded approved diagnostic path. Extra hops need a revised exact contract. [ASP.NET proxy guidance](https://learn.microsoft.com/en-us/aspnet/core/host-and-deploy/proxy-load-balancer?view=aspnetcore-10.0).

| Configuration | Proposed exact format/invariant |
|---|---|
| Application discriminator | `IGAMigrationTool.Bff.<environment-id>.v1`; reviewed non-secret stable environment label, immutable across replicas/compatible revisions; separate repositories/keys across environments |
| Ring object | `https://<dedicated-control-plane-account>.blob.core.windows.net/bff-data-protection/keyring.xml`; exact private object, no query/SAS; no customer artifacts in container |
| Wrapping key | `https://<reviewed-vault>.vault.azure.net/keys/bff-data-protection`; versionless for new wrapping, actual versioned reference retained on each protected ring key |

| Supported implementation | Microsoft `Azure.Extensions.AspNetCore.DataProtection.Blobs` and `.Keys`; exactly pin/audit required versions before implementation and prove their real ETag conflict/recovery behavior |

A discriminator isolates purposes but a shared repository is still a compromise boundary; use distinct environment stores/keys. Missing persistence/wrap/unwrap denies; no plaintext/ephemeral production ring. Use the supported Blob repository's conditional write/ETag protocol; test concurrent creation/rotation rather than hand-building it. [Data Protection configuration](https://learn.microsoft.com/en-us/aspnet/core/security/data-protection/configuration/overview?view=aspnetcore-10.0), [Microsoft Blob repository](https://github.com/Azure/azure-sdk-for-net/blob/main/sdk/extensions/Azure.Extensions.AspNetCore.DataProtection.Blobs/src/AzureBlobXmlRepository.cs).

Proposed runtime access, **not grants**: custom key role with exactly `Microsoft.KeyVault/vaults/keys/read`, `Microsoft.KeyVault/vaults/keys/wrap/action`, `Microsoft.KeyVault/vaults/keys/unwrap/action` scoped to that key; custom dedicated-container Blob read/write without delete/role administration. Exact Blob actions and provider access need proof. Key/container creation, rotation administration, recovery, SQL administration and role grants remain separate named operators. Built-in alternative Key Vault Crypto Service Encryption User is narrower than Crypto User but includes extra EventGrid management actions; accepting it requires reviewing that surplus, not calling it exactly three actions. [Built-in role](https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles/security#key-vault-crypto-service-encryption-user).

Versionless wrapping does not unwrap old data with the newest version. Preserve all historical wrapping versions required by stored protected data and its recoverable backups. Rotation intervals, deletion eligibility, Blob recovery, vault purge protection, session/challenge cleanup and recovery owner remain actual lifecycle decisions; audit12months is not a key-retention default. Old disposable-session vault settings cannot be copied into production. [Key rotation](https://learn.microsoft.com/en-us/azure/key-vault/keys/how-to-configure-key-rotation).

Warm replicas can retain Data Protection keys after key/grant revocation; cryptographic revocation is not immediate session invalidation. Incident procedure must also update authoritative subject versions/revocation and drain/restart affected replicas. Key deletion can destroy decryptability and is never a shortcut for product logout. [Key management](https://learn.microsoft.com/en-us/aspnet/core/security/data-protection/implementation/key-management?view=aspnetcore-10.0).

## Migration, compatibility, failure and rollback

Existing001/002 remain historical. New module-owned schemas are additive after local approval, populated only by explicit synthetic migration/administration in tests. Existing authority lacking enrollment/cutoff/role/audit binding denies. No production seeding, blanket backfill or client-supplied assignment import. Rollback disables admission, preserves audit/version/tombstone/key state and uses reviewed compatible readers; never decreases a security version, restores revoked sessions or drops records to make an older build run.

Read/provider/key/audit failure produces generic denial with no credentials or identity payload. Broken privacy/integrity or contradictory authority blocks the operation. Local role isolation must prove runtime cannot bypass commands. Product known-change revocation and provider eventually consistent evidence remain distinct. Ordinary logs contain only allowed categories/correlation and are neither the audit record nor evidence of successful access.
