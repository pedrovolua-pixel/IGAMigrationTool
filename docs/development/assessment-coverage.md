# Assessment coverage reconciliation (local foundation)

`AssessmentOrchestration.SyntheticBaselineInventoryPlanner` is the internal cycle-02 fixture boundary for baseline inventory to coverage planning. It accepts only `synthetic-baseline-inventory-v1`, an already-authorized opaque customer/project/environment scope, a value-free inventory, an explicit permission descriptor, the existing exact-version compatibility descriptor and caller-supplied category applicability. This is not the feature-001 manifest schema or a receiving/import adapter. It does not verify source payload digests, eligibility, freshness, retention, authorization or rule applicability.

After the existing capability guard succeeds, it freezes baseline identity, scope, permission-warning state, exact lock, sorted objects/categories, coverage keys and explicitly declared `not_applicable`, `not_assessed` or `unsupported` items. `RequiresAssessment` leaves the key outstanding and never creates a pass/finding. Exact duplicate category metadata deduplicates; contradictory declarations, duplicate object IDs and duplicate supplied native-identity tuples return typed refusal without a plan. Native identity may be absent, as the approved evidence contract allows; the baseline-local ID remains required. An unknown fixture version, wrong scope, blocked permission, malformed metadata, absent installed module or empty inventory also returns no plan. Permission warnings remain visible but no audit event is emitted by this pure projection. Refusal does not reconcile or discard a source baseline's duplicate records.

Use the returned keys with `CoverageProgressProjector` while results are missing, and with the existing terminal composition once every key has a valid result. This executable synthetic path does not implement a trusted production baseline reader, complete inventory/applicability planner, durable start/retry/cancellation/checkpoint state, UI, health scoring or feature/E2E acceptance. Those remain open in the canonical local build and feature plans.

`AssessmentOrchestration.CapabilityBoundCoverageProjector` composes exact-version locking with the existing terminal coverage projections. Its caller supplies trusted capability/baseline descriptors and a trusted, already-authorized inventory plan and results. A failed capability lock or invalid/incomplete coverage returns typed issues and no combined projection. Success snapshots the exact lock, completion kind, terminal counts, executable numerator/denominator and gap limitations. It has no source adapter, inventory/applicability inference, authorization implementation, persistence or durable run transition. Its module reference to `AssessmentCoverage` adds no external package. The separate versioned `tests/integration/SyntheticPilotFlow.Tests` executable tests independently expected synthetic cases; it is not the full end-to-end pilot.

`AssessmentCoverage` is an internal Phase 1A foundation for FR-HAS-2, FR-HAS-8 and TP-HAS-001. Given a trusted plan of inventory/evidence-category keys and terminal results, it requires exactly one result for every planned key. It rejects missing, duplicate, unexpected or malformed keys; invalid states; and gap states without a structured reason code and responsible stage. It never infers a pass from absent evidence.

The allowed terminal states match the approved technical specification: `pass`, `finding`, `not_applicable`, `not_assessed`, `insufficient_evidence`, `excluded`, `inaccessible`, `redacted`, `unsupported`, and `error`. Gap reason and responsible stage must be present; their exact format is left to the approved evidence contract. The result contains issue codes and internal keys for a caller to handle under authorization; callers must not put keys or protected evidence into ordinary logs.

This component does not build the expected inventory, decide applicability, access the feature-001 baseline, authorize a user, score health/quality, activate a run or publish a result. The full TP-HAS-001 and G2/G3/G4 gates remain `NOT VERIFIED`. Thirteen local synthetic cases exercise completeness, duplicates, unexpected results, typed gaps, invalid states/keys and empty-plan behavior.

`CoverageCountProjector` snapshots its inputs and exposes unweighted counts for each terminal state only after the same reconciliation passes. It returns issues and no projection for missing, duplicate, unexpected or malformed results. It calculates no score or percentage. Four additional synthetic cases include a 100,000-item count exercise; this is a local fixture, not an end-to-end scale or performance claim.

`CoverageLimitationProjector` also requires a reconciled plan. It groups `not_assessed`, `insufficient_evidence`, `excluded`, `inaccessible`, `redacted`, `unsupported`, and `error` by terminal state, opaque reason code and responsible stage. `pass`, `finding`, and `not_applicable` do not become limitations. Missing results or unexplained gaps yield no projection. Five synthetic cases verify grouping, every limitation state and fail-closed behavior. Reason codes and stages remain internal metadata; callers must authorize and sanitize them before any external display. This is one input to the future separate quality report, not the complete `pilot-quality-v1` calculation.

`CoverageProgressProjector` permits missing results while a run is still underway and reports planned, terminal and remaining unit counts plus terminal-state counts. It shares the reconciler's input validation but does not allocate an issue for every missing key during progress polling. Duplicate, unexpected, malformed or unexplained results deny the projection. Six synthetic cases include a 100,000-key not-started plan. `AllTerminal` means only that every trusted planned key has a terminal coverage item; it does not complete, score, authorize or publish a run.

`ExecutableCoverageProjector` computes the `pilot-quality-v1` executable-coverage counts only after full reconciliation. `pass` and `finding` contribute to the executed numerator; explicit `not_applicable` units leave the applicable denominator; all other terminal states remain in the denominator. A zero denominator is identified as no applicable units, not perfect coverage. The projector exposes counts without a rounded percentage, health score or run-completion decision. Six synthetic cases cover gaps, no applicable units, invalid results and 100,000 planned units. [Partial bootstrap run 36901896983](https://github.com/pedrovolua-pixel/IGAMigrationTool/actions/runs/36901896983) passed across Linux and Windows runners. The trusted plan and applicability decision remain external dependencies.
