## Scope and components

A separate opt-in loopback synthetic evaluation workspace reuses the pinned React19/TypeScript7/Vite8 dependencies in `src/web/package.json` and lock unchanged. New frontend files live only under `src/web/evaluation/`, including its own entry HTML, TypeScript/Vite configuration, stylesheet and focused checks. The coordinator owns the dedicated host and shared wiring; the existing consultant application, source adapters, `App.tsx` and `AnalysisView.tsx` remain untouched.

The fixed fictional fixture contains120 source members and100 frozen selected members. The source, population, sample and original findings cannot be edited by this workspace. One server-trusted qualified Consultant has two exact environment assignments. Assignment and qualification details are read-only server projections. The browser neither chooses an actor nor submits roles, grants, categories, qualifications, scope authority or registry changes. No assignment administration, risk acceptance, report publication, task creation, source access, execution, download/export or provider operation is added. The host stays explicitly enabled and loopback-bound; local fixture semantics do not grant real authority.

## Visible workspace and labels

Use a restrained single workspace in the existing consultant style: warm light background, dark green masthead, system body type, serif title, accessible native controls and explicit focus outline. A CSS dark color scheme provides the same hierarchy. No remote images, fonts, analytics or animations are needed.

The masthead reads **“Evaluation review”**, badge **“Local synthetic fixture”**. The introduction states **“Review this frozen cohort. Original conclusions and prior outcome versions remain unchanged.”** A persistent notice reads **“Full pilot acceptance is not verified. This workspace uses fictional evidence and server-seeded assignments.”** Source manifest links are display-only opaque metadata; digests are integrity identifiers, never authority or external evidence links.

The main view shows these parallel sections:

1. **Frozen cohort**:120 source members,100 selected members,40 mandatory Critical/High members and60 selected lower-severity members (15 environment A,45 environment B). Display source/population/sample digests and immutable version bindings in an expandable **“Source locks”** panel. Show mandatory/sample distinction, originating environment/module/category/severity, rule and model/prompt version and unavailability where permitted. No remove, replace, suppress, re-rank or resample action.
2. **Accuracy and sample limits**: server-supplied current immutable outcome version and predecessor; Confirmed, Rejected, Indeterminate, Unreviewed, Corrected counts; the reviewed non-indeterminate denominator; exact overall confirmation ratio or **“No reviewed denominator”**. Corrected is labelled **“Corrected outcomes overlap their originating classification; they are not added again to the denominator.”** Warnings remain separate from eligibility and acceptance. Low-sample warning reads **“Fewer than30 reviewed outcomes: interpret this ratio cautiously.”** Server accuracy targets do not become a client-computed gate.
3. **Selected members**: a labelled filter/list of100 selected IDs and originating classification, with explicit one-member selection; selection renders **“Original conclusion”** beside **“Current review”**, read-only **“Current assignment”** and the action editor if authorized. Unavailable, no-eligible or denied selected items remain selected and Unreviewed until an authorized command exists; do not label denial Indeterminate or provide actor impersonation controls.
4. **Outcome versions**: current version and earlier immutable versions by server version number. Prior version mode is explicitly read-only, with **“Historical outcome version — review actions are unavailable.”** Older snapshots do not inherit current disclosure permission. **“Related history”** is requested independently using the server's current history decision; a scoring/presentation grant is never treated as history authority.

Protected detail and historical records are never preloaded as a hidden authorization substitute. Synthetic original conclusion/rationale/evidence labels render as text nodes. Evidence references are opaque text with no inferred URL, raw-evidence resolver or executable affordance.

## Read admission and authority

All successful and failed network responses are parsed against the exact closed shared DTO schema before use: reject missing/extra keys, unknown enums, wrong types, duplicate IDs, invalid references/digests/revisions/times, impossible counts and inconsistent source/member/current-version relations. The UI validates response schema and integrity fences; the server is the sole outcome and authority source. Canonical JSON is kept as exact bytes/text and verified using SHA256 before trusting its associated digest; do not parse and stringify it to compare digests. Recompute only integrity hashes, never sampling, policy, outcomes or accuracy. Exact envelope/body admission and canonical locks are frozen in the shared domain contract.

A successful complete read is visibly **“Current workspace loaded”** only after all admitted source/member/version/digest relations agree. Metadata-only, partial, malformed, stale or hash-failing reads are unavailable, show a typed neutral state, clear protected details/history/editor/command state and disable commands. An old successfully loaded object is not presented as current while refresh or reauthorization is pending. A current-policy denial is shown **“Review unavailable under the current assignment.”** Revocation or inactive identity/assignment clears protected member and history content immediately upon the response. This browser cannot promise instantaneous revocation without a server exchange; explicit refresh and every operation recheck current server policy.

## Commands and explicit draft lifecycle

The reviewer chooses exactly one outcome **Confirmed**, **Rejected**, **Indeterminate** or **Corrected** and enters a required rationale plus admitted synthetic evidence-reference vector. Corrected additionally requires explicit originating classification (Confirmed/Rejected) and one or more documented correction dimensions and proposed values. The original conclusion remains visible and is never replaced by the edited presentation. Evidence refs are reference IDs only; no raw upload or external links.

The command includes only the shared permitted command fields, exact current source/cohort/aggregate/member/registry expectations and a browser-generated UUID idempotency key. Those expectations come from the just-admitted complete read, not user-editable authority fields. A command is impossible for historical mode, denied eligibility, unavailable permitted context (except explicitly eligible Indeterminate semantics), absent source locks or unresolved read failure. The domain contract determines the exact correction/category/grant distinction; the browser exposes only the separately authorized action.

**“Prepare review”** validates the local draft and creates an immutable prepared body and UUID. A summary identifies selected member, action, rationale, evidence refs, correction origin/dimensions and expected immutable version. **“Record review”** sends that exact body once. The controls and member/version selection are disabled while sending; request completion is accepted only for the same selected member, source digest, read epoch, prepared body and request identity. A successful response is validated and the UI displays **“Review recorded in outcome version N.”**, clears the draft/prepared command and reloads complete current state. The trusted store creates this immutable outcome version automatically. No **Freeze**, **Publish**, manual version creation or client-generated outcome exists.

A transport failure leaves **“Result unknown. Refresh to inspect the current version, or retry this exact prepared review.”** and **“Retry same review”**; retry reuses the original UUID and byte-identical body. Never automatically retry, change the body, bind the command to a refreshed revision, create a new UUID or interpret a timeout as failed/no-write. A retry may be denied by current server policy and then clears protected content. A revision/source/policy conflict shows **“Workspace changed. Refresh and prepare a new explicit review.”** and disables the prepared action. Refresh invalidates the old draft/prepared command; after inspected current state the reviewer explicitly chooses and prepares a new action. An accepted retry receipt does not count as a second outcome.

## Async fences and failures

Use monotonically increasing read epochs and AbortController plus immutable source/evaluation/member/version fences. Abort is not proof a server mutation was cancelled. Switching member/version, refresh, unmount, denial or invalid response invalidates pending detail/history requests and drafts. Responses from earlier epochs cannot repopulate protected content, overwrite a newer selection/version or enable a command. Mutation responses cannot silently rebound to another selected member; after sending, an unknown result remains inspectable through explicit refresh. History has its own loading/denied state and epoch; it never replaces the main current-policy decision. Complete workspace/prior-version projection requires the current separately granted RelatedHistory permission across all100 selected members; a per-member history read checks that member’s current scope. No partial workspace is silently treated as complete.

Server typed denials produce generic issue text, no submitted-value echo. Unknown HTTP status/body, unexpected content type, response-too-large, network failure, invalid digest or unexpected source gives **“Workspace unavailable. Refresh before reviewing.”** No JSON/debug payload, stack trace, rationale telemetry or console logging. Body limits, reference-vector limits and text-length limits are bound to the closed shared contract. No browser persistence, local/session storage or payload logging; reload discards drafts and obtains current policy.

## Shared closed command freeze candidate

The JSON object has exactly these keys: `eventId`, `memberId`, `kind`, `expectedAggregateRevision`, `expectedMemberRevision`, `expectedRegistryVersionId`, `expectedSourceDigest`, `expectedSampleDigest`, `outcome`, `originatingClassification`, `reason`, `evidenceReferenceIds`, `correction`. No other key is permitted. `kind` is Review or PresentationCorrection. `eventId` is a nonempty UUID; references use existing maximum128-character ASCII synthetic-reference grammar; digest fields are64 lowercase hexadecimal. Revisions are safe JavaScript integers>=0. `reason` is1–2000 UTF16 code units. Evidence refs are sorted unique, at most16. Correction is null or exactly `{severity,category,rootCause,recommendation}`, each nullable or1–2000 UTF16 units. Severity/category corrections are presentation text, never changes to immutable classification or authorization category.

Review outcome is Confirmed, Rejected, Indeterminate or Corrected. Corrected requires at least one correction value and origin Confirmed or Rejected. Other review outcomes forbid origin and correction. PresentationCorrection requires outcome/origin null plus at least one correction value. It preserves prior classification; only an existing Confirmed/Rejected classification may become the overlapping Corrected projection, never synthesize a scored result from Unreviewed/Indeterminate. UI names the separate editor **“Presentation correction”** and shows it only under the independently granted presentation action. All submitted source/registry/member expectations are copied from admitted server state. Server request processing authenticates its fixed actor and rechecks current authority; possessing expectations/digests grants no authority.
