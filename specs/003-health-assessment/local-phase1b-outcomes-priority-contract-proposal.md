## Desired-outcome content and lifecycle

A stable outcome belongs to one fictional customer/project/environment. Each immutable version contains an opaque outcome ID, positive monotonic version number, title, desired behavior, applicability to existing fictional units, `documented` or `inferred` origin, fact/inference/assumption labels, bounded fictional evidence/reference IDs, predecessor if present, content-contract version and content digest. An inferred draft remains visibly inferred after review/approval; approval does not turn an inference into an observed fact. No free SQL, executable criterion, attachment, source fetch or external reference resolver is introduced. Fixed fixtures define outcomes and their criterion/unit links; a human reviews the displayed exact version.

Content never changes in place, including drafts. Creating revised content creates a new draft version under the same stable ID and retains the predecessor. Lifecycle events are immutable; a current projection derives status from those events. Each event captures its exact content version/digest, trusted actor/scope, continuous revision, database UTC time, command UUID and required nonblank reason (at most 2000 UTF-16 units, exact preserved text). Old lifecycle events and approval decisions remain readable under current authority. This is local fictional retention, not a new customer retention policy.

| Current state | Allowed next state/action | Trusted fictional actor and conditions |
| --- | --- | --- |
| Absent version | `draft` | Assigned synthetic Consultant; exact fixture content and source/applicability validation |
| `draft` | `consultantReviewed` | Assigned synthetic Consultant; explicit review of complete exact content with reason |
| `draft` or `consultantReviewed` | `retired` | Assigned synthetic Consultant; abandon advisory candidate with reason |
| `consultantReviewed` | `customerApproved` | Distinct fictional customer outcome approver; exact Consultant-review event, content digest and current revisions |
| Prior `customerApproved` when a reviewed successor is approved | `superseded` | Same fictional customer approval transaction; successor shares stable ID/scope and is later version; both events commit atomically |
| `customerApproved` | `retired` | Distinct fictional customer outcome approver; explicit withdrawal with reason |
| `superseded` or `retired` | None | Terminal version; a later candidate is a new draft |

No direct draft approval, advisory supersession, self-transition, backward transition, deletion or automatic restoration. Creating a draft/reviewed successor leaves the currently approved predecessor effective. Approving a successor replaces only the same stable ID; a first approval has no supersession event. Approval is monotonic against the highest ever approved version for this stable ID, including superseded/retired history: a new approval must have a strictly greater version number. Retiring v3 therefore cannot make still-reviewed v2 approvable. Exact accepted approval replay retains its historical receipt without reapproval. Retiring an approved version leaves no current approved version; it does not revive a superseded predecessor. Unsupported transitions do not reserve a command UUID or write history.

A narrow verified adapter translates each exact locked approved version into the scorer's existing `ScoringOutcome` and unit outcome links. ## Original fictional priority policy

Priority is recommendation-option metadata bound to exact run, finding, option, guidance/source digest, policy version and original factor vector. It is distinct from finding severity, health, maturity, artifact review and task state. The proposed policy uses decimal arithmetic:

`P = 100 × (0.30S + 0.20E + 0.15A + 0.15D + 0.10Q + 0.10O)`

| Factor | Exact fictional normalization | Fixture default when expressly supplied by the fixture |
| --- | --- | --- |
| Severity `S` | Critical 1; High 0.8; Medium 0.45; Low 0.2; Informational 0 | Original finding severity, with its exact source version |
| Exposure `E` | Isolated 0; Internal 0.25; Partner-facing 0.5; Public-facing 1 | Internal = 0.25; a labeled fictional assumption |
| Affected objects `A` | `min(distinct scoped affected-object count, 100) / 100`; nonnegative integer count | Actual distinct fictional occurrence-object IDs; no grouped-row count substitute |
| Dependency criticality `D` | None 0; Ordinary 0.25; Important 0.5; Essential 1 | Ordinary = 0.25; a labeled fictional assumption |
| Effort quick-win factor `Q` | XS 1; S 0.75; M 0.5; L 0.25; XL 0 | S = 0.75 from the locked fictional proposed estimate; approval status remains visible |
| Customer objectives `O` | Maximum matched weight from the exact locked fictional objective map, each in `[0,1]`; no matching objective in a complete map = 0 | A complete versioned fictional map: access governance 1, operational resilience 0.75, maintainability 0.5; option matches are fixture references |

Objective mapping is a separate declared planning assumption; it never grants outcome approval or produces an adherence score. Its map/version/digest and option-match references are frozen. Use the highest matched weight rather than summing multiple objectives. Unknown/missing exposure, dependency, effort, objective map or invalid count produces Priority unavailable with explicit missing inputs. The stated fixture defaults are actual recorded inputs, not runtime fallback rules for unknown customer values. Validate each enum, weight, count, source link and arithmetic bound; unknown policy versions fail closed.

Priority labels use the **unrounded** value: Immediate `P >= 80`, High `60 <= P < 80`, Medium `40 <= P < 60`, Low `P < 40`. Display one decimal with the existing away-from-zero convention; show the raw value in the explanation. Sort available items descending raw `P`, then ordinal scoped finding ID, then ordinal option ID; unavailable items follow with the same identity tie-break. Show original factors/contributions and fixture assumptions. For example High/Internal/10 distinct objects/Ordinary/S/access governance yields `P = 51.75`, displayed `51.8`, Medium; this is a proposed independent test vector, not executed evidence.

## Effort approval and reasoned overrides

The locked original estimate consists of relative size, inclusive person-hour interval, estimator-policy version, assumptions, prerequisites and source references. Proposed `synthetic-effort-policy-v1` fictional ranges are XS 1–2, S 2–8, M 8–24, L 24–80 and XL 80–160 person-hours. Adjacent boundaries may overlap. These ranges exist only to exercise the workflow; they are not customer estimates, elapsed delivery durations or vendor benchmarks. Display Proposed fictional estimate until the Consultant explicitly approves the exact estimate/source digest.

The assigned Consultant can append an approval for the original estimate, or a reasoned replacement estimate using one allowed size and that size's exact fictional range. Each replacement includes assumptions/prerequisites and explicit Consultant approval in one event. A separate explicit priority override chooses one allowed priority label and requires a reason; the automated raw value, factors and label remain visible. Do not create a fake numerical score for a label override. Withdrawing an active same-source override is a reasoned event restoring the original effective value; all earlier decisions remain. An effort withdrawal restores Approved original fictional estimate only if an earlier explicit approval of that exact original estimate/source exists; otherwise it restores Proposed fictional estimate. The replacement approval does not approve the original. No active override means a new withdrawal is Invalid state with no write; exact accepted withdrawal replay remains available. A changed/unavailable source cannot receive a new withdrawal, approval or override; refresh and explicitly approve the new exact source instead. Old-source approvals remain historical, not current. Only one latest effective priority decision and one latest effective effort approval/override apply per exact source.

Approving/changing effort does not recalculate the original formula; it was calculated from the frozen original vector. If the Consultant wants a different planning priority, they explicitly record a priority override. This avoids a hidden side effect and preserves original-versus-effective rationale. Changed sources require explicit new-source approval/override; old events remain historical and cannot be silently rebound. If source is unavailable/corrupt, suppress mutation and show only verified permitted metadata. An effort approval and a priority override neither change finding disposition nor review artifacts, complete tasks, validate remediation or authorize execution.

The UI shows original and effective priority, original and current approved effort, exact approval/override reason and source freshness with progressive disclosure. Required text renders inertly; invalid Unicode round-trip, oversized strings and unknown command fields deny before persistence. Security/operational audit is payload-free; product history contains authorized reasons, separate from audit.

## Transaction, retry and compatibility constraints

Use additive outcome and recommendation-planning records owned by their modules; no cross-module SQL. Freeze exact schema, DTO, canonical bytes, digests, bounded list/text sizes, lock inventory, receipt and error shapes in an independently reviewed implementation contract before code. Share owning-module APIs and one coherent transaction for outcome approval/supersession/start locking; do not open a nested independent connection while holding its fence.

Commands carry exact source/version/event vector, expected revisions and actor-bound UUID. Validate closed shape, current authority/category scope and stored integrity first. Accepted exact semantic replay returns its original immutable metadata receipt without restoring current state; changed accepted UUID reuse conflicts. For a new UUID, stale expected source/revisions conflict with no write; state/actor eligibility then applies. Event, current projection and receipt commit atomically. Cross-outcome/run/actor UUID substitution, missing history, revision gaps and corrupt projections deny. On uncertain responses retain the exact command for explicit Retry; refresh after receipt/conflict and reject late replies from another selected source.

The coordinator composes one new opt-in localhost fictional Phase 1B profile for the combined outcome/priority, automatic-AI and CSV closure slices. Freeze its exact ID, complete per-profile lock inventory, private schema/DTO and application-contract versions after the related owner decisions; this proposal does not reserve an independent twelfth-profile meaning. Outcome/priority code must require its exact approved locks and the complete combined inventory, never accept partial combinations. All eleven previous profiles retain exact input/analysis shapes, saved envelopes, digests and validators, including the existing Cycle14 task profile. No reinterpretation of historical synthetic outcome flags is allowed. Use an expressly owned dedicated synthetic database guard and additive migrations; do not alter prior migration bytes. No new dependency is justified.

Task/artifact originals, attestation vectors, historical receipts, workflow and freshness remain governed by their approved contracts. Priority/effort events belong to recommendation planning metadata and do not modify generated guidance/artifact content or the existing task source binding. They cannot auto-convert/reconfirm/reopen a task or withdraw/review an artifact. Existing tasks retain their exact creation/reconfirmation provenance. Task displays may link to separately labeled current/historical recommendation planning metadata after authorization; they must not present it as frozen task creation data. Any proposal to add priority/effort to task conversion bindings or CSV must be separately frozen and reviewed with the coordinator's task/export contract before implementation.

Rollback disables new-profile actions and retains immutable local history; no downmigration, truncation or data purge. No customer retention, production schema, external task, provider, report publication, reassessment or permission change is authorized. Shared/canonical records and private-site updates belong to the coordinator after an attributable decision and executed evidence.

## Alternatives and remaining acceptance

A Consultant approving both review and customer acceptance would erase the approved distinction; the proposed distinct fixture makes that boundary testable. Production customer roles would change a security boundary and need separate human design approval. Scoring inferred drafts would violate FR-HAS-7. Reading latest approved outcome status at score time would rewrite historical behavior. An unspecified priority formula or silently assumed customer duration would leave FR-HAS-36 untestable.

Approval completion: repository owner explicitly selects/amends OP1B-01–06 and cites the exact reviewed proposal revision/digest. Then the coordinator freezes implementation contracts, execution packets and test oracles, obtains independent engineering review, implements and verifies the bounded new profile, and updates canonical status/site. Full Phase 1B closure additionally requires its complete authorized local exit evidence; operational pilot, manual accessibility and customer gates remain independently NOT VERIFIED until executed.
