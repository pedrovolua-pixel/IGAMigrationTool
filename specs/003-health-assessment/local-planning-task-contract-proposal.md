## Conversion and identity

A task corresponds to one existing scoped recommendation option and its complete fictional artifact set, not to each artifact or occurrence. Its stable identity includes customer, project, environment, run, finding and scoped option identity; source digest, workflow state and creation command UUID are not identity components. An identical option in another run is a different task; no cross-run deduplication/reassessment correlation is introduced.

Creation previews the current original option, prerequisites, risks, validation/recovery guidance, all three unchanged Unverified original artifacts, current Reviewed for planning attestations and finding warning. The consultant explicitly confirms conversion and supplies a reason. A proposed finding is not thereby confirmed; accepted-risk handling remains with the existing owning module and unsupported local states are not invented. Finding rejection or missing/unavailable source suppresses new conversion/reconfirmation; an existing task remains historical.

The server captures the complete current run/locked input/guidance/package/finding source plus the selected artifacts' latest accepted review events/revisions under the same run transaction fence as the task write. Artifact attestations must all belong to that exact source. A source digest alone is insufficient because withdrawal/re-review changes attestation state without changing the package digest. Unselected artifact-attestation changes do not invalidate this option's task; complete package/finding-source changes do.

Creation and each reconfirmation preserve metadata bindings and permitted immutable original-source references required for a verifiable read. Generated artifacts remain Unverified and inert. Do not duplicate raw/protected customer evidence into a task; the proposed slice uses fixed fictional content only. Freeze the exact retention/classification and source-reference representation internally before code, without creating a customer retention policy or claiming deployed blob storage.

## Workflow and source freshness

| Current state | Permitted status targets |
| --- | --- |
| Planned | In progress, Cancelled |
| In progress | Planned, Completed, Cancelled |
| Completed | Planned — explicit reopen |
| Cancelled | Planned — explicit reopen |

No self-transition; comments are separate events. New tasks start Planned and are assigned to the trusted creating Consultant. There is no arbitrary title editing, due date, assignment picker, priority, effort, attachment, mention, external notification or deletion operation.

Freshness is separate from workflow. Current source and selected attestations exactly matching the latest creation/reconfirmation binding give Current plan. A verified later source/attestation mismatch gives Needs reconfirmation. Missing/invalid/unavailable proof gives Source unavailable; it is never treated as Current. A completed task can become stale without becoming reopened or validated closed automatically.

Entering In progress or Completed requires Current plan and a non-Rejected current finding. Reopening Completed/Cancelled explicitly returns to Planned, requires a verifiable non-Rejected current source and may leave Needs reconfirmation; it never marks new-source work completed. While stale or newly Rejected, an authorized Consultant may append a comment in any state, cancel only from Planned/In progress, or return In progress to Planned, using an exact verified current-source/attestation precondition; missing/corrupt source denies all writes. A new Reconfirm plan is allowed only in Planned/In progress with Needs reconfirmation; an already Current plan cannot receive a redundant binding event (Invalid state, no write). Exact accepted reconfirmation replay remains independent of later freshness. A new reconfirmation requires the original scoped finding/option still to exist, non-Rejected status and all selected current artifacts Reviewed for planning. It adds a binding event without changing task status. Completed/Cancelled tasks must explicitly reopen before reconfirmation. If unavailable, retain authorized task metadata/history with a bounded unavailable marker only when stored integrity and current category/assignment authority can be verified; hide unverifiable content and suppress actions. Never fall back to unfenced generation or bypass access controls to show history.

Comment/reason strings render as inert ordinary text. Invalid Unicode round-trip, missing/unknown fields, oversized input and unsafe revisions fail before writes. Security audit/operational telemetry excludes comments, reasons, source content and generated artifacts; product task history is a separate authorized domain record.

## Concurrency, replay and durable records

- Capture source once inside the owning database transaction, after acquiring the shared run fence and before task row locks. All source and selected artifact-review writers join it. Settle a same-transaction module-owned attestation read API before coding; existing artifact ReadAsync opens another connection/transaction and must not be called while holding the fence elsewhere.
- Validate closed command fields/bounds first (Create always declares initial expected task revision0). Under the fence, validate trusted authority/resource/category visibility, verifiable current source/selected-attestation vector and stored task/history integrity, then inspect the accepted UUID namespace. Exact accepted replay returns its original receipt; changed accepted UUID reuse conflicts. Neither reapplies new-command source/revision/transition eligibility.
- For a command with no accepted UUID, first compare complete expected current source and selected current attestation event/revision vector; a mismatch is a conflict with no write. For Create, look up the stable task identity next: if present, return Already exists/task ID independent of its current revision/status and current non-Rejected/all-reviewed creation eligibility. Expected revision0 means absence precondition only for actually creating a task; it is not compared to an existing task's later revision on this duplicate branch. If absent, require non-Rejected source/all three current artifacts Reviewed for planning and create from revision0 atomically. For reconfirm/status/comment on an existing task, compare expected task revision, then exact transition/freshness eligibility before committing. New actions require fresh explicit inspection.
- Store immutable creation, reconfirmation, status and comment events with actor, trusted UTC time, continuous task revision and an atomic current projection plus metadata-only receipt. Schema drift, missing rows, gaps, inconsistent receipt/projection and source rollback fail closed.
- Accepted event UUIDs are unique across the scoped run/task module and bound to actor, task and complete semantic command; a UUID cannot identify another task/action. A fresh duplicate Create returns only Already exists and the existing scoped task ID after the preceding authority/visibility/integrity and exact-current source/vector checks. This branch may return the existing identity after a newly withdrawn/Rejected source is explicitly inspected, because it creates or confirms nothing; an absent task still fails creation eligibility. It reserves no event UUID, writes no event/current/receipt and never returns or updates a creation receipt; changed-reuse conflicts apply to UUIDs already accepted. The UI rereads the existing task and requires explicit reopen/reconfirmation when appropriate.
- Exact replay is actor/scope/task/semantic-command bound. It may return its original accepted receipt after later events/source changes, once current authority/visibility and verifiable current source/history integrity pass. Current artifact withdrawal or a later workflow state does not reapply creation eligibility to an already-accepted replay; missing/corrupt source denies replay until a verifiable read is available. It does not restore that state, source binding or current view. Changed reuse of an event UUID conflicts.
- The UI retains an uncertain exact command for explicit Retry, validates the closed original receipt and rereads the coherent task/source view. Conflicts preserve entered text but require refresh and a new explicit command. Late replies and run/option selection races cannot restore stale views.

An implementation contract must freeze exact schema/DTO/canonical digests/limits/error shapes and transaction composition before independent writing packets. Those engineering details must implement this decision without inventing additional product choices. If review discovers a consequential departure, amend the proposal before implementation.

## Compatibility, rollout and rollback

The new profile is the eleventh local profile. Its saved task-contract lock and application/source versions are explicit; ten historical saved envelopes and existing artifact review remain byte-compatible. Current source validators require exact per-profile inventories rather than accepting optional fields generally. The additive task schema never changes old migration bytes or rewrites artifact/finding review records. No dependency is currently justified.

Enable only with an explicit local task flag and dedicated `iga_synthetic_cycle14_` database ownership guard. Disabled hosts and older profiles expose no task authority. Implement through existing modular architecture, fixed fictional sources and bounded interfaces; [ADRs0001/0002/0003/0004](../../architecture/decisions/README.md) remain accepted. No new deployment topology, customer-data plane or renderer architecture is approved here.

Rollback disables new task/profile actions and retains compatible immutable history/source references. No downmigration, truncation or purge to restore an earlier application. Production data retention, identity, assignment/revocation, export, deletion/hold and recovery acceptance remain with their existing gates.
